🎯 Critérios de Comparação

Refinados com base nas suas preferências:

  • Enforcement: Permissão ou hooks — prompt NÃO é enforcement (aprendizado com mnemory/DCP)
  • Routing de modelos: Capacidade de usar modelo caro (Pro/Opus) pra planejamento/revisão e barato (Flash/Mimo) pra execução
  • Pipeline: Linear, fan-out, async, loops — com estimativa de custo×velocidade
  • Persistência: Estado cross-session (mnemory já cobre, mas plano/tracks podem ser adicionais)
  • Integração com seu setup: Conflita com AFT/DCP/memory/hooks?
  • Maturidade: Stars, releases, contribuidores, licença
  • Custo controlável: Dá pra limitar paralelismo?
  • Resiliência: Retry, fallback, recovery?
  • Flexibilidade: Dá pra trocar partes sem quebrar o todo?

🔒 Plugin de Enforcement Descoberto: cc-safety-net

Durante o estudo, você descobriu o cc-safety-net (kenryu42) — plugin de enforcement de comandos destrutivos no shell. Não é um orquestrador, mas fecha o gap de enforcement real que você identificou como prioridade.

kenryu42/cc-safety-net ⭐ —

Plugin PreToolUse hook · 19 releases · MIT

Instalação: opencode plugin -g cc-safety-net (fonte)

Custom Rules (fonte):

Sim, você configura o que quer bloquear via rulebooks em .cc-safety-net/rules/rule.json. Schema:

CampoDescrição
version1 (schema atual)
rulesLista de rulebook sources (ex: ["project-rules"])
overridesDesabilitar regras ou trocar razões

Cada rulebook (.cc-safety-net/rules/<nome>/rulebook.json) contém:

CampoDescrição
nameNome do rulebook
allowed_commandsComandos que este rulebook pode criar regras (ex: ["git", "npm"])
rulesArray de regras com name, command, subcommand, block_args, reason
testsFixtures: command + expect (blocked|allowed) + rule

Exemplo — bloquear npm install -g:

{
  "rulebook_version": 1, "name": "project-rules", "version": "1.0.0",
  "allowed_commands": ["npm"],
  "rules": [{
    "name": "block-npm-global",
    "command": "npm", "subcommand": "install",
    "block_args": ["-g", "--global"],
    "reason": "Use npx ou local install."
  }],
  "tests": [
    {"command": "npm install -g typescript", "expect": "blocked", "rule": "block-npm-global"},
    {"command": "npm install typescript", "expect": "allowed"}
  ]
}

Fluxo de trabalho com custom rules:

  1. npx -y cc-safety-net rule init — cria starter config
  2. Edita rulebook.json com suas regras
  3. npx -y cc-safety-net rule sync — sincroniza
  4. npx -y cc-safety-net rule verify — valida
  5. npx -y cc-safety-net rule test — roda fixtures

Relevância pro seu setup:

Seu gapComo cc-safety-net ajuda
Sem enforcement de comandos destrutivos✅ Bloqueia rm -rf /, git push --force, etc. antes de executar
Permission deny rules do OpenCode são fracas (bypass)✅ Análise semântica + recursão de wrappers
Plugin de hooks não detecta comandos perigosos✅ Complementar — cc-safety-net detecta, seu hook age depois

Riscos: Falha fechada (se config inválida, BLOQUEIA TUDO). Use --dry-run da CLI explain pra testar antes de commit.

⚖️ Decisão: Construir ou Adotar?

Três caminhos possíveis

🛠️ Caminho A: Construir seu próprio

O que seria: Criar seu template config OpenCode com base nos patterns estudados, usando seu plugin de hooks para enforcement.

Vantagens: Controle total, só o que precisa, sem overhead de ecossistema externo. Integração perfeita com AFT/DCP/memory.

Riscos: Tempo de desenvolvimento, erros de design, sem benchmark de validação.

Inspiração: Pegar o melhor de cada template: enforcement do fmflurry, 2 tiers do small-orchestrator, lane system do grojeda, tracks do supersimple.

✅ RECOMENDADO — É o que faz mais sentido pro seu perfil

📦 Caminho B: Adotar um existente

Melhor candidato: small-opencode-orchestrator (#28) — mesmos modelos que você, 10 agents, 2 tiers, plugin plan-post-approval. Ou planning-with-files pra começar mais simples.

Vantagens: Pronto, testado, comunidade.

Riscos: Overhead de features que não usa, conflito com setup existente, dependência de terceiros.

Segundo candidato: fmflurry — se quiser o enforcement mais forte e contínuo learning. Mas usa modelos diferentes dos seus.

📖 Segunda opção — small-orchestrator ou planning-with-files

Riscos: Complexidade de integração, dois sistemas evoluindo separadamente.
